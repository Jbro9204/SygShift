# Existing Email Sending provider reference

Reviewed 10/19/2026 against deployed Worker source `54d021cd85e137739d5db33c9cf7418b613bf4d0`, the isolated notification candidate, and the official Cloudflare contract. **Prepared only; no production deployment or provider send.**

The deployed source calls `environment.EMAIL.send` with a structured object containing sender, recipient, subject, HTML, and text. `wrangler.jsonc` configures the native `send_email` binding named `EMAIL`; it does not construct a legacy raw `EmailMessage`. The [official Email Sending Workers API](https://developers.cloudflare.com/email-service/api/send-emails/workers-api/) documents the structured send result as `EmailSendResult` with an opaque string `messageId`. Its existence is documented for this exact transport. The deployed helper awaited that result without retaining it and always passed NULL to `service_log_email_delivery.target_provider_reference`. The earlier report's source-level observation is therefore correct.

The narrow forward code change captures a nonempty string `messageId` per normalized, deduplicated recipient and passes it to the existing audit RPC for accepted inline and deferred deliveries. It never infers an ID from error text, exception metadata, timestamps, recipient hashes, or message content. Missing/invalid acceptance metadata still produces a successful send with a NULL audit reference. Rejected or suppressed deliveries have no accepted provider reference. No transport, binding, credentials, API authorization, database schema, RPC signature, or historical row is changed. The existing audit RPC's trimming/200-character storage contract is retained.

An associated safety correction separates provider-send failure from accepted-send audit failure. Inline audit errors now retain acceptance and emit only a sanitized `email_delivery_audit_deferred` signature. They cannot add the accepted recipient to `failed`, trigger another send, or cause the caller to record delivery failure. Deferred queue processing continues to make its accepted terminal marker durable before attempting the audit. Its existing scheduled containment behavior remains intact. Provider-reference metadata is internal; the welcome API retains its existing three-field delivery JSON.

This improves future persisted audit correlation only. If audit storage is unavailable, that attempt's provider ID may still fail to persist; the sanitized log is not a durable audit retry mechanism. No historical missing ID is reconstructed, and this change cannot establish the rejected recipient's identity in the stranded broadcast. The unknown handoff blocker and no-resend requirement remain.
